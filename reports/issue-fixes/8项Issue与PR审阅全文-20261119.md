## F17 FP32 exp2 底数错误

<a id="f17-issue"></a>

### Issue

**[XPU] P800 cluster 上 FP32 `tl.math.exp2(3)` 返回 20.085537，预期为 8**

在 FlagTree 提交 `e6a8799cc` 上复现了 #1248 的数值问题。普通 Triton kernel 可以编译并执行，但 `tl.math.exp2(x)` 输出了自然指数。例如，`x=1` 时得到 2.718282，`x=3` 时得到 20.085537。[已有 issue #1248](https://github.com/flagos-ai/FlagTree/issues/1248) · [复测提交](https://github.com/flagos-ai/FlagTree/commit/e6a8799cc14819def1bdb8fe68b018fd774fe4c9)

#### 环境

昆仑芯 P800（KL3），PyTorch `2.9.0+cu129`，使用 Torch 的 CUDA 兼容接口。内核以 FP32 输入和输出运行，显式设置 `is_sdnn=False`、`num_warps=8`、`num_stages=1`。脚本只依赖 Torch 和 FlagTree 提供的 Triton。

#### 最小复现

保存为 `reproduce.py`，在可访问 P800 的容器中运行 `python reproduce.py`。参考值在 CPU 上以 FP64 计算，再转回 FP32。

```python
import torch
import triton
import triton.language as tl


@triton.jit
def kernel(src, dst, BLOCK: tl.constexpr):
    i = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    tl.store(dst + i, tl.math.exp2(tl.load(src + i)))


if __name__ == "__main__":
    x = torch.tensor([-3., -1., 0., 1., 3., -2., 2., 0.], dtype=torch.float32).repeat(1024)
    device_x = x.cuda()
    device_y = torch.full_like(device_x, float("nan"))
    kernel[(1,)](device_x, device_y, 8192, num_warps=8, num_stages=1, is_sdnn=False)
    actual = device_y.cpu()
    expected = x.double().exp2().float()
    print("x, actual, expected:", x[:5].tolist(), actual[:5].tolist(), expected[:5].tolist(), flush=True)
    torch.testing.assert_close(actual, expected, rtol=2e-6, atol=0)
```

#### 实际与预期

| 输入 | −3 | −1 | 0 | 1 | 3 |
|---|---:|---:|---:|---:|---:|
| 原版 P800 输出 | 0.049787 | 0.367879 | 1 | 2.718282 | 20.085537 |
| 预期输出 | 0.125 | 0.5 | 1 | 2 | 8 |

原版在 8192 个元素中有 6144 个超出容差。另用 256 和 8192 两种分块运行 65536 元素的回归用例，两种分块都完成编译、均因数值断言失败。这个结果对应 #1248 中的底数错误；该 issue 后续在 main 上复测，5 种分块均能编译，底数错误仍在。[#1248 复验](https://github.com/flagos-ai/FlagTree/issues/1248#issuecomment-6191097671)

<a id="f17-pr"></a>

### PR

**[BACKEND] Preserve base-2 semantics for FP32 exp2 on the XPU cluster path**

Addresses the incorrect numerical result reported in #1248. On P800, a plain Triton kernel evaluating `tl.math.exp2(3.0)` returns `20.085537`. With this change it returns `8.0`. A later retest in the issue compiled all five block sizes and still observed the base error. [Retest on main](https://github.com/flagos-ai/FlagTree/issues/1248#issuecomment-6191097671) [Issue #1248](https://github.com/flagos-ai/FlagTree/issues/1248)

#### Implementation

The XPU cluster pipeline runs `TritonXPULegalizeExternEW` before converting Triton to the XPU dialect. The backend lowers `math.exp` through LLVM's `exp2` intrinsic to the KL3 instruction `exp.f.rn`, which computes the natural exponential. The original legalization patterns allow an explicit base-two exponential to reach that path without the change of base. [Pass registration](https://github.com/flagos-ai/FlagTree/blob/e6a8799cc14819def1bdb8fe68b018fd774fe4c9/third_party/xpu/backend/compiler.py#L495) · [Existing exponent lowering](https://github.com/flagos-ai/FlagTree/blob/e6a8799cc14819def1bdb8fe68b018fd774fe4c9/third_party/xpu/lib/Conversion/TritonXPUToLLVM/ElementwiseOpToLLVM.cpp#L192) · [Documented instruction semantics](https://github.com/flagos-ai/FlagTree/blob/e6a8799cc14819def1bdb8fe68b018fd774fe4c9/third_party/xpu/lib/Dialect/TritonXPU/Transforms/LegalizeExternEW.cpp#L11)

Add a rewrite for ranked FP32 tensor `math.exp2` operations. It emits an FP32 multiply by `ln(2)` followed by `math.exp`, using the input tensor type for the constant. This implements `2ˣ = exp(x × ln(2))` in the existing cluster pipeline.

#### Regression coverage

Add a device test for blocks of 256 and 8192 elements. It checks 65536 FP32 values against a CPU FP64 base-two reference rounded to FP32, including negative and positive integers, ±120, both infinities, and NaN. The test uses zero absolute tolerance, so underflowing the reference value at −120 to zero would fail.

```bash
python -m pytest -q third_party/xpu/python/test/unit/language/test_xpu_exp2.py
```

| P800 check | Official base | With the patch |
|---|---:|---:|
| Standalone reproducer, 8192 elements | 6144 mismatches | Passed |
| Device regression, block sizes 256 and 8192 | 2 failed on values | 2 passed |

Both builds use commit `e6a8799cc`, identical XPU toolchain packages, and the same physical P800. Device validation covers KL3. The existing cluster legalization pass is shared, and this rewrite has no architecture guard; behavior on other XPU generations has not been measured. [Base commit](https://github.com/flagos-ai/FlagTree/commit/e6a8799cc14819def1bdb8fe68b018fd774fe4c9)

此前 GDN 工单指出了同一异常处理逻辑，另一条 compare-fusion 工单记录了类型校验时出现的容量误报。这里附上只验证异常分类的四个 IR，方便维护者独立复现。[#1126](https://github.com/flagos-ai/FlagTree/issues/1126) · [#1249](https://github.com/flagos-ai/FlagTree/issues/1249)

### PR

**[BACKEND] Preserve verifier errors from the XPU make_ttxir pipeline**

The XPU Python backend wraps every pass manager failure in `OutOfResources`. A downstream caller can therefore interpret an invalid branch type or store type as an SRAM allocation failure. The same wrapper was reported in two application issues. [#1126](https://github.com/flagos-ai/FlagTree/issues/1126) · [#1249](https://github.com/flagos-ai/FlagTree/issues/1249)

#### Change

In `XPUBackend.make_ttxir`, retain resource reporting for `OutOfResources` and for diagnostics containing the allocation markers listed in the patch. Re-raise other exceptions so the caller receives their original type and diagnostic. The change is confined to the Python backend. [Patch](../../work/2026-11-13/flagtree-101-review/flagtree/F20/review.patch)

#### Validation

On P800/KL3 at `e6a8799cc`, replayed three branch-shape inputs and one BF16 store input. All four passed input verification. The original backend rejected all four with the additional SRAM classification. With the patch, the same four compilations still failed at the relevant verifier and exposed the underlying error without the SRAM classification. These inputs exercise the non-resource branch. They do not establish coverage of every message a genuine allocator failure can produce. [Before](../../work/2026-11-13/flagtree-101-review/flagtree/F20/evidence/official.json) · [After](../../work/2026-11-13/flagtree-101-review/flagtree/F20/evidence/solution.json)

## U05 标量 tanhf 饱和区与负零

<a id="u05-issue"></a>

### Issue

**[XPU] P800 的标量 FP32 tanh 对 ±100 返回 NaN，并丢失负零**

#### 现象与影响

在 P800 上调用 `libdevice.tanh` 时，标量路径对 `+100` 和 `+∞` 返回 NaN，预期为 `+1`。对 `−100` 和 `−∞` 也返回 NaN，预期为 `−1`。接近零时，`−0` 和 `±2⁻²⁶` 都变成了 `+0`，FP32 结果本应保留输入值和符号。

这个错误会传到融合算子的输出。原生 Inductor 将 BF16 Add + GELU（tanh 近似）编译为单核，内部以 FP32 调用 tanh。在 64×1024、零偏置、遍历全部 65,536 种 BF16 位型时，官方版有 31,842 个输出的 NaN 判定与 eager 参考不符。[生成的融合核](../../work/2026-11-13/P800-9-issue-pr-review/U05/evidence/operator-fusion/generated-kernel.txt) · [P800 融合实测](../../work/2026-11-13/P800-9-issue-pr-review/U05/evidence/operator-fusion/verification.json)

#### 原因

标量函数先求 `u = exp(x)`，再计算 `(u − 1/u) / (u + 1/u)`。当指数或倒数溢出，分子和分母同时成为无穷大，结果变成 NaN。对于极小的输入，`u` 和 `1/u` 都可能舍入为 1，分子相减得到零。[官方标量函数源码](https://github.com/flagos-ai/FlagTree/blob/e6a8799cc14819def1bdb8fe68b018fd774fe4c9/third_party/xpu/device/trigonometric.xpu#L1211)

#### 复现

```bash

```

普通 Triton 和 TLE 各测两次，分别使用默认设置和显式关闭向量化。官方版 1/4 通过，仅 TLE 默认设置通过。小数和负零在显式关闭向量化时逐位比较。[逐项输出](../../work/2026-11-13/P800-9-issue-pr-review/U05/evidence/code-review/official-regression.log) · [对应 PR 草稿](#u05-pr)

### PR

**[XPU] Handle saturation and preserve tiny inputs in KL3 scalar FP32 tanh**

Related issue: [P800 scalar tanh returns NaN for ±100 and loses negative zero](#u05-issue).

#### Change

Fix `tanhf` in the XPU device library shared by regular Triton and TLE. For `abs(x) >= 16`, FP32 tanh already rounds to a signed unit, so return `copysign(1, x)` before computing the exponential. For `abs(x) <= 2⁻¹²`, return `x` to preserve its correctly rounded value and the sign of zero. The existing expression handles the remaining inputs, including NaN. An earlier compiler-pass fix missed the TLE scalar path.

Add four regression cases covering regular Triton and TLE, each with default and disabled vectorization. The scalar cases also compare tiny values and signed zeros bit for bit. [Code and regression test](../../work/2026-11-13/P800-9-issue-pr-review/U05/review.patch)

#### P800 validation

Tested on physical card 7 (KL3, shared mode) using the same personal Docker image, PyTorch `2.9.0+cu129` and fresh kernel caches. The unmodified and patched device libraries were built from official base `e6a8799cc` with the same toolchain and loaded by the same compiler.

## U09 切分 scf.if 后的分支类型

<a id="u09-issue"></a>

### Issue

**[XPU] P800 编译 Add + LayerNorm 时，切分后的 scf.if 与分支返回类型不一致**

用 FlagTree 编译三份来自 FP32 Add + LayerNorm 的 TTIR 时，输入均通过 MLIR 校验，随后在 `TritonXPULegalize` 中失败。例如，循环内的 `scf.if` 有三个张量结果。编译器把结果切成 8×1024，而分支仍返回 16×1024 的常量张量。外层将异常包装为 `OutOfResources: uni_sram`，内部 verifier 指明了不匹配的返回类型。[官方版原始诊断](../../work/2026-11-14/U09-review/official/results.json)

基线为官方提交 `e6a8799cc`。该版本处理循环内的条件分支时，先按旧结果类型检查 else 的 `yield`，随后才切分 `if` 的结果，且没有按新类型重新检查 then 的 `yield`。常量可以定义在分支外，即使分支里的运算已经切分，分支仍可能引用原尺寸。[官方源码](https://github.com/flagos-ai/FlagTree/blob/e6a8799cc14819def1bdb8fe68b018fd774fe4c9/third_party/xpu/lib/Dialect/TritonXPU/Transforms/Legalize.cpp#L1451)

### PR

**[BACKEND] Rebuild captured splat yields after slicing XPU scf.if results**

Addresses [the P800 scf.if result type mismatch](#u09-issue).

#### Change

When the XPU legalizer slices a loop-nested if, set its result types before reconciling the branch terminators. Inspect both present branches in the nested and outer if paths. For a dense constant whose entries all have the same value, rebuild the constant at its use in the branch with the full target tensor type. The element type must match. Other uses keep the original constant. [Code and regression test](../../work/2026-11-14/U09-review/review-with-test.patch)

Add a compiler regression test that parses a captured FP32 Add + LayerNorm input, verifies it, runs the default KL3 make_ttxir pipeline and verifies the result. It requires the XPU compiler bindings and uses no device eager operations.

#### Validation

Tested on P800/KL3 in Docker against official base e6a8799cc and the build with only this legalizer change. The Python backend fingerprint matched across builds. All three original inputs and three equivalent controls with inverted conditions and exchanged branches passed input verification. The official compiler failed all six at TritonXPULegalize. The patched compiler verified all six and emitted ELF and XPUBIN for each. Each original/mirrored pair produced identical XPUBIN bytes. [Official diagnostics](../../work/2026-11-14/U09-review/official/results.json) · [Patched artifacts](../../work/2026-11-14/U09-review/patched/results.json)

The proposed pytest failed on the official compiler and passed on the patched compiler. A 32-row tile of generic1 ran on physical card 3. All 65,536 FP32 outputs met the CPU reference tolerance (atol and rtol 3e-4), with maximum absolute error 1.90735e-6. Full 2048×2048 numerical validation on cards 3 and 7 timed out. A separate reduced synthetic input advanced past legalization but failed a later unroll-control pass with an SSA dominance error.
